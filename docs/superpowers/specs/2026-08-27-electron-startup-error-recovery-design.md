# Electron 启动错误与恢复机制设计

## 背景

Electron 当前把 Python 子进程成功创建视为“正在运行”，但此时驱动、摄像头和识别器可能尚未准备完成。Python 能在 stderr 中打印“无法打开摄像头”等具体原因，Electron 渲染层却只收到退出码，因此打包版通常只能显示通用的 `process exited (1)`，也无法在界面内重新启动。

本轮只修复阻断启动和恢复流程的 P1 问题，不改变手势识别、关节映射、急停、受控恢复和真机控制行为。

## 目标

- Python 用机器可读事件报告启动阶段、就绪状态和致命错误。
- GUI 展示用户可以理解的错误原因，而不是只有退出码。
- 无摄像头、驱动连接失败和运行中摄像头断开都返回正确的失败状态。
- GUI 提供显式“重试启动”，不要求用户关闭并重新打开程序。
- Electron 同一时间最多维护一个 Python 子进程。
- 真机驱动不自动重连；只有用户明确点击重试后才重新启动。

## 非目标

- 本轮不自动枚举或切换摄像头。
- 本轮不自动反复重启 Python 或真机驱动。
- 本轮不修改摄像头编号配置方式。
- 本轮不修改识别、映射、发送、急停或恢复算法。
- 本轮不把完整 Python traceback 直接展示给普通用户。

## 错误根因

1. Electron 主进程只解析 Python stdout 中的帧消息，stderr 仅转发到后台日志。
2. Python 的驱动失败、摄像头打开失败和未捕获异常最终都只表现为子进程退出。
3. Electron 在 `spawn` 后立即发送 `running: true`，它表示“进程存在”，不是“程序可用”。
4. 摄像头连续读取失败会跳出循环并返回 `0`，错误地表现为正常退出。
5. preload 没有重启 API，渲染层失败后只能禁用控件。

## 生命周期协议

Python stdout 继续只承载逐行 JSON 协议，stderr 继续承载诊断日志。Electron 模式启动时，程序先复制原 stdout 文件描述符供 Bridge 独占，再把进程级 fd 1 重定向到 stderr。这样 OpenCV、MediaPipe 和厂商 DLL 绕过 Python `print`、直接写 stdout 时，也不会破坏 JSON 协议。协议新增以下事件：

```json
{"type":"status","phase":"driver","state":"starting"}
{"type":"status","phase":"camera","state":"starting","camera_index":0}
{"type":"ready"}
{"type":"fatal","code":"CAMERA_OPEN_FAILED","message":"无法打开摄像头 0","retryable":true}
```

第一轮错误码：

| 错误码 | 含义 | 可重试 |
| --- | --- | --- |
| `CONFIG_ERROR` | 配置文件读取或校验失败 | 是 |
| `DRIVER_CONNECT_FAILED` | 灵巧手驱动连接失败 | 是，必须由用户触发 |
| `CAMERA_OPEN_FAILED` | 摄像头无法打开 | 是 |
| `CAMERA_READ_FAILED` | 运行中持续无法读取摄像头帧 | 是 |
| `RUNTIME_ERROR` | 未分类运行异常 | 是 |

`ready` 只在驱动和摄像头均初始化完成后发送。首帧仍然是渲染画面可见的最终依据，但不再承担唯一的后端就绪信号。

## Electron 状态机

Electron 主进程维护四种状态：

- `starting`：Python 已创建，后端仍在初始化。
- `ready`：Python 报告就绪，可以等待或接收首帧。
- `failed`：收到结构化 fatal，或子进程意外退出。
- `stopped`：用户退出或窗口关闭导致的预期停止。

子进程退出时，主进程保留最近一条结构化错误。如果退出前没有 fatal，则生成通用 `RUNTIME_ERROR`，并附带退出码供诊断。最终状态在 ChildProcess `close` 而不是 `exit` 事件结算，确保 stdout 中最后一条 fatal 已被读取；已结算运行的迟到消息会被忽略。用户主动退出不得显示为故障。

## 错误界面

启动失败后，启动动画停止并替换为清晰的错误面板：

- 标题：例如“无法打开摄像头”。
- 说明：例如“未能打开摄像头 0，请检查连接、系统权限或摄像头占用情况。”
- 主操作：“重试启动”。
- 次操作：“退出程序”。
- 辅助信息：错误码和退出码，可供排查但不抢占主视觉。

错误容器使用 `role="alert"`，失败后将键盘焦点移到“重试启动”。运行中异常退出时，清空旧的 `SENDING` 状态，并在画面区域显示同一错误面板。

## 重试安全边界

- 重试必须由用户点击触发，不进行自动重启。
- 主进程开始重试前确认旧进程已经退出。
- 启动中重复点击只产生一个 Python 子进程。
- 重试会清空旧错误、旧帧和旧遥测，再重新进入 `starting`。
- 真机模式下，重试可能重新执行驱动连接和初始化，因此界面文案提醒用户确认灵巧手周围安全。
- 用户关闭窗口或点击“退出程序”时，Electron 会先阻止自身退出，通知 Python 正常清理摄像头和 CAN-FD；子进程关闭后才放行应用退出，超时才强制结束后端。

## 测试与验收

### Python

- 驱动连接失败发送 `DRIVER_CONNECT_FAILED` 并返回非零状态。
- 摄像头打开失败发送 `CAMERA_OPEN_FAILED` 并返回非零状态。
- 连续读取摄像头帧失败发送 `CAMERA_READ_FAILED` 并返回非零状态。
- 初始化完成后发送一次 `ready`。
- Electron bridge 关闭时仍释放识别器、摄像头和驱动。

### Electron

- 解析 `status`、`ready` 和 `fatal`，并保留现有 frame 协议。
- `spawn` 成功只进入 `starting`，不能直接进入 `ready`。
- fatal 或异常 exit 显示错误原因并启用重试。
- 用户主动退出不显示错误。
- 连续点击重试不会创建重复 Python 进程。
- 错误面板具备可见标题、重试和退出按钮。

### 手动验收

1. 使用不存在的摄像头编号启动，确认显示“无法打开摄像头”并可重试。
2. 插入摄像头后点击重试，确认进入实时画面。
3. 运行中拔出摄像头，确认显示“摄像头读取失败”，不显示退出码 `0`。
4. 真机模式点击重试前出现安全提示，并且系统中只有一个 Python 进程。
